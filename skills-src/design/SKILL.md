# design

Per-folder architecture documentation, kept fresh against git history.

See `~/newstack/brain/DESIGN_SKILL_SPEC.md` for the system-level spec: the file
layout, why DESIGN.md is universal rather than per-language doc files, and how the
constraint-binding mechanism works.

## Modes

Read the matching reference file, then follow it. Do not improvise a mode.

| Invocation | Reference | Cost | What it does |
|---|---|---|---|
| `/design check [--folder P\|--touched]` | `references/drift-check.md` | free | Reports stale folders. Pure git, no source reads, no subagents. |
| `/design map [--print]` | `references/map.md` | cheap | Regenerates root `MAP.md` by collating `.design.yaml` files. No source reads. |
| `/design rebuild [--folder P] [--force]` | `references/rebuild.md` | expensive | Regenerates `DESIGN.md` + `.design.yaml` per folder. Parallel subagents. |

Bare `/design` with no mode: run `check` and report. It is the cheap one, and its
output tells the user whether a rebuild is worth it.

The normal sequence is `check` to find drift, `rebuild` to fix it, then `map` to
refresh the root artifact. Each mode stays independent so the cheap ones can run on
every PR without dragging the expensive one along.

## The artifact set

Every qualifying folder gets exactly two files, and the repo root gets one.

1. **`<folder>/DESIGN.md`** - rich-markdown architecture document with inline Mermaid
   diagrams, an entity table, gotchas, and cross-folder dependency links. Renders
   natively on GitHub. Fully skill-owned and rewritten from scratch on each rebuild.
2. **`<folder>/.design.yaml`** - machine-readable sidecar. Carries the freshness
   anchor that `check` reads and the metadata that `map` collates.
3. **`MAP.md`** at the repo root, a one-page tour generated by `map`.

Nothing else. The skill never touches `doc.go`, `README.md`, `lib.rs`, `mod.rs`, or
any other language-native doc file. Those stay human territory, and symbol-level docs
belong on the symbols themselves in source.

## Which folders qualify

A folder qualifies if it holds substantive source code (more than roughly 3 files of
the relevant language), has at least one entity worth naming, and is not a
pass-through container.

Skip `vendor/`, `.git/`, `node_modules/`, `dist/`, `build/`, `target/`,
`__pycache__/`, `.next/`, `.nuxt/`, `bower_components/`. Skip generated code, using
the heuristic that a file opens with `// Code generated ... DO NOT EDIT.` or its
equivalent, in which case skip the whole folder. Skip `cmd/` and its subfolders,
`examples/`, `internal/cmd/`, and `tests/fixtures/`, which are pass-through
containers where a DESIGN.md carries little value. Skip folders that are only data,
config, or fixtures.

Ask the user when a folder is borderline. Less is more.

## Freshness model

`last_rebuilt` in each sidecar is the only freshness signal, and every sidecar
written during one rebuild carries the same SHA so the anchor stays consistent across
the pass. A folder is fresh when that SHA is still an ancestor of HEAD and nothing
under the folder has changed since. Anything else is drift, including a SHA that fell
out of history through a force-push or a squash. In that case report drift and let a
rebuild re-anchor it.

A folder with no `.design.yaml` is not an error. It may legitimately be a
pass-through, a fixture directory, or simply never rebuilt. Report it and move on
without pressure-creating sidecars.

## `.design.yaml` schema

```yaml
package: <folder identity, typically the folder basename>
purpose: "<one-sentence purpose>"
language: go              # informational only, drives /design map's "Languages:" stat line
last_rebuilt: <commit SHA at rebuild time>
last_rebuilt_at: 2026-...
entities:
  - name: <e.g. LocalAuth, LocalAuth.HandleSignup>
    kind: <struct|interface|func|method|class|type|const|...>
    role: "<one line: what it is>"
    why: "<one line: design rationale, constraint, or gotcha>"
depends_on:               # filled by rebuild's Pass 2; Pass 1 leaves empty
  - path: ../core
    entities: [User, IdentityStore, ChannelStore, ...]
```

`language:` is informational. No mode branches on it except `map`, which uses it to
render one stat line. The schema is identical regardless of the folder's language.

`doc_file:` and `diagrams_file:` from prior iterations are removed. The skill always
writes `<folder>/DESIGN.md`, so there is nothing left to declare.

## Quoting: `purpose`, `role` and `why` are always double-quoted

These three carry generated prose, and prose collides with YAML constantly. An
unquoted value is a plain scalar, and a plain scalar cannot start with a backtick or
a quote character and cannot contain `: `. All three happen naturally when you are
describing code:

```yaml
role: `ListApps` on a fresh store returns an empty slice.   # BREAKS: leading backtick
role: RFC 7662 introspection, returns {Active: false}.      # BREAKS: contains ": "
why: '~'-prefixed parts are excel-base-decoded.             # BREAKS: leading quote
```

So: **always wrap `purpose`, `role` and `why` in double quotes.** Inside them, escape
`\` as `\\` and `"` as `\"`. Prefer backticks over double quotes when you name an
identifier, which keeps the escaping rare.

```yaml
role: "`ListApps` on a fresh store returns an empty slice."
role: "RFC 7662 introspection. Returns {Active: false} for any invalid token."
why: "`PublicMethods` keys are matched against `info.FullMethod`; a typo silently turns into \"auth required\"."
```

`name`, `kind`, `package`, `language`, `last_rebuilt` and `depends_on` are identifiers
and SHAs. Leave them unquoted.

There is a fourth case, and it is the one that does not announce itself. An unquoted
value containing ` #` is truncated at the hash, with no parse error at all:

```yaml
why: Kept distinct because DCR has no place for quota fields; see issue #189.
# YAML reads: "Kept distinct because DCR has no place for quota fields; see issue"
```

Issue and PR references are exactly the thing a `why` line wants to cite, so this is
common. Five values had already been quietly clipped in the repo the rule came from,
and nothing had flagged them because the file parsed fine.

Getting this wrong fails silently. A sidecar that does not parse is invisible to every
consumer, so `/design check`, `/design map`, and diffpp's `review_prior` all skip it,
and a broken file reads as an undocumented folder rather than as an error. Nine of one
repo's twenty-one sidecars were lost this way before the rule existed.

## Validation: every sidecar must parse before a pass reports success

Whatever the quoting rule, generated YAML needs a machine check. After writing a
sidecar, parse it. Use whichever parser the machine has:

```bash
# ruby ships with macOS and most Linux; pyyaml and yq are common alternatives
validate_yaml() {
  if command -v ruby >/dev/null;  then ruby -ryaml -e "YAML.load_file('$1')" && return; fi
  if command -v yq >/dev/null;    then yq '.' "$1" >/dev/null && return; fi
  python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" "$1"
}
validate_yaml "<folder>/.design.yaml" || { echo "INVALID: <folder>/.design.yaml"; }
```

A parse failure is a bug in the file you just wrote, not in the parser. Fix the
quoting and re-check before reporting the folder done.

## Principles shared by all modes

- **Language-agnostic.** The sidecar schema does not vary by language, and no mode
  needs to know whether a folder holds Go, TS, Rust, or anything else.
- **Never auto-commit, never auto-branch.** Every mode leaves its output in the
  working tree for the user to review with `git diff` and commit or restore.
- **Report rather than act**, except where the user asked for the write. `check` never
  writes. `map` writes only `MAP.md`. `rebuild` writes only `DESIGN.md` and
  `.design.yaml`.
- **Malformed sidecars are surfaced, not silently skipped.** A file that fails to
  parse or lacks a `purpose:` gets listed in the mode's summary so the user can fix it
  and rerun.
